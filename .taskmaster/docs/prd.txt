# Overview

Willab is a Next.js frontend for practice interview sessions. Users sign in with Supabase. Students have a single homework flow at /dashboard. Admins manage students and homework configuration at /admin/students and /admin/students/:id. The BFF (Next.js API routes) proxies to a Flask backend at v2; frontend calls use /api (no v2 in path).

# What is in place (frontend)

Admin panel: Students list and profile. Per-student warm-up tasks (with max_performance_score 0-1 in UI). Focus tasks from global pool. Post-recording questions (exactly 3). Metrics (5 fixed, label edit). Speaker profile (Context textarea). Reports history. Send Homework. All BFF routes under /api/admin and /api/homework.

Student app: One flow only at /dashboard. Step 1: Start session, show warm-up task text and recorder; upload recording_1. Step 2: Show task text and two metric question inputs; submit metric answers. Step 3: Show final task text and recorder; upload recording_2. Step 4: If backend returns questions, show form and submit; else skip to report. Step 5: Show report text and performance_score_end. Flow auto-starts on load. BFF mock available when NEXT_PUBLIC_API_URL unset or MOCK_HOMEWORK_BACKEND=1 so the flow runs without backend.

API paths: Frontend calls /api/homework/session/start, /api/homework/session/:id/recording-1, metric-answers, recording-2, questions, post-answers, task-block. BFF proxies to backend /v2/homework/session/start and /v2/homework/session/:id/... Backend URL from NEXT_PUBLIC_API_URL or NEXT_PUBLIC_BACKEND_URL or BACKEND_URL. Real-time recording UI: wheel (strength/pace) only, client-side (useRealtimeStrengthPace, AnalyserNode); no PCM chunk or glow. Strict taskmaster: step only from GET status (five values); no default warm-up text (empty → “Warm-up prompt unavailable. Please refresh.” + Refresh); status unknown → error + Refresh; after POST start call GET status and apply; 422 NO_WARMUP_CONFIGURED blocks with message.

# What remains (backend and specs)

Backend homework endpoints: Implement POST /v2/homework/session/start (return session_id and warm_up_task_text; use last report performance_score_end and warm-up selection algorithm to choose warm-up). Implement POST recording-1 (transcribe, extract context, compute performance_score_1, choose focus_task by score, return task text and metric questions). Implement POST metric-answers (return final_task_text). Implement POST recording-2 (compute performance_score_2). Implement GET questions and POST post-answers (report generated on post-answers; performance_score_end). All contracts and API paths are in .taskmaster/docs/APP_DESCRIPTION.md.

Warm-up selection: Backend implements selection (max_performance_score per warm-up, eligible filter, anti-repetition, etc.) per backend spec. Admin API warm-up GET/POST/PUT must accept and return max_performance_score (0-1).

Final task LLM: Define exact prompt and constraints for the model that builds final_task_text from context and focus_task and metric answers. Document in a backend or LLM spec; frontend already displays final_task_text.

Report content: Backend generates report to include coaching for both recording_1 and recording_2 and commentary on how the student stuck to the metrics. performance_score_end is the final score.

# Development roadmap

Phase 1 Backend homework flow: Implement all homework student endpoints so the frontend flow works end-to-end with a real backend. Add max_performance_score to warm-up task schema and admin API; implement warm-up selection on session start (see backend spec).

Phase 2 Scoring and content: Define and implement performance_score_1 and performance_score_2 formulas. Define final_task LLM prompt and constraints and implement. Ensure report generation uses context, both recordings, reflective answers, and metrics adherence.

Phase 3 Polish: Any admin UX improvements, reporting history enhancements, or student-facing tweaks based on usage.

# Logical dependency chain

Backend homework endpoints and warm-up selection must be implemented first so the student flow is end-to-end. Scoring formulas and final_task LLM spec can follow. Report content spec is a small doc update; implementation is backend.
